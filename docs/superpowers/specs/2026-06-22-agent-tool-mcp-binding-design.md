# Agent-Tool 统一治理与 Agent-MCP 绑定设计

## 背景

当前平台已经有统一工具运行层，`ToolRegistry` 聚合 `ToolProvider`，并把工具定义暴露给聊天运行时。MCP 服务管理已支持维护 MCP Server、同步 MCP Tool、全局启停服务和工具。Skill 侧已经有 Agent-Skill 绑定，运行时会根据 Agent 或用户选择注入 Skill 摘要，并通过 `skill.read` 工具渐进读取完整说明。

目前 MCP 工具仍按全局可见处理。只要 MCP Server 和 MCP Tool 被启用，所有 Agent 都可能看到这些工具。这不符合 Agent 治理诉求，也不利于控制高风险外部工具的使用范围。

本设计采用统一 Agent-Tool 治理模型，首版只落地 MCP Tool 级绑定。管理端可以表现为“Agent-MCP 绑定”，底层使用统一 `agent_tool_binding`，为后续接入 `sandbox.*`、`skill.*` 或其他工具来源保留同一治理入口。

## 目标

- 新增统一 Agent-Tool 绑定模型。
- 首版只支持 `provider_type = MCP`，绑定粒度为 MCP Tool。
- 未显式绑定 MCP 工具的 Agent 默认不可见任何 MCP 工具。
- MCP 运行时暴露工具时同时满足三层控制：MCP Server 启用、MCP Tool 启用、Agent 已绑定。
- MCP 工具执行侧做二次授权校验，避免只依赖 `listTools` 过滤。
- 管理端在 Agent 管理页新增“绑定工具”操作，与现有“绑定 Skill”并列。
- 保持现有 MCP 服务管理、Skill 绑定、Sandbox 工具和聊天 SSE 流程不退化。

## 非目标

- 首版不把 `sandbox.*` 纳入管理端绑定。
- 首版不把 `skill.read` 纳入管理端绑定，Skill 仍由 Agent-Skill 绑定控制。
- 首版不做权限模板、危险级别审批、批量策略、组织级继承或租户级工具策略。
- 首版不改变 MCP Server 和 MCP Tool 的全局管理页面。
- 首版不改变 MCP 协议接入方式、MCP Client 行为和调用日志格式。

## 概念关系

```text
Agent = 谁来工作
Skill = 怎么工作
Tool = 能做什么动作
MCP = 接入外部工具的一种协议和来源
```

MCP Server 是工具集合入口，一个 MCP Server 可以暴露多个 MCP Tool。例如：

```text
GitHub MCP Server
  - search_repositories
  - get_issue
  - create_issue
  - delete_repo
```

平台同步后暴露给 LLM 的工具命名为：

```text
mcp.github.search_repositories
mcp.github.get_issue
mcp.github.create_issue
mcp.github.delete_repo
```

治理分三层：

```text
mcp_server.enabled    控制整个 MCP 服务是否全局可用
mcp_tool.enabled      控制某个 MCP 工具是否进入平台全局可用池
agent_tool_binding    控制某个 Agent 是否被授权使用该工具
```

## 方案选择

采用方案 B：统一 `agent_tool_binding`，首版只展示和执行 MCP Tool 绑定。

备选方案：

- MCP 专用绑定表：实现直观，但后续接入其他工具来源时会出现多套绑定模型，治理割裂。
- 统一 Tool 绑定表：与现有 `ToolRegistry` 抽象一致，首版范围可控，后续扩展自然。
- 只保存配置不接运行时：交互上像治理，实际 MCP 工具仍全局可见，不满足本次治理目标。

推荐方案的关键约束：

- 绑定表是统一模型。
- 首版服务层只允许保存 MCP 工具。
- 管理端首版只展示 MCP 工具。
- 运行时首版只对 `mcp.*` 做 Agent 级过滤。

## 数据模型

新增表 `agent_tool_binding`：

```sql
CREATE TABLE agent_tool_binding (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    agent_id BIGINT NOT NULL,
    tool_name VARCHAR(256) NOT NULL,
    provider_type VARCHAR(32) NOT NULL,
    provider_ref_id BIGINT NOT NULL,
    enabled BOOLEAN NOT NULL DEFAULT TRUE,
    sort INT NOT NULL DEFAULT 0,
    created_by BIGINT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_by BIGINT,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT fk_agent_tool_agent FOREIGN KEY (agent_id) REFERENCES agent_config (id) ON DELETE CASCADE,
    CONSTRAINT uk_agent_tool_binding UNIQUE (agent_id, tool_name)
);

CREATE INDEX idx_agent_tool_agent_sort
    ON agent_tool_binding (agent_id, sort, id);

CREATE INDEX idx_agent_tool_provider_ref
    ON agent_tool_binding (provider_type, provider_ref_id);
```

字段说明：

- `tool_name`：暴露给 LLM 和运行时分发的完整工具名，例如 `mcp.github.search_repositories`。
- `provider_type`：工具来源类型，首版只允许 `MCP`。
- `provider_ref_id`：来源侧记录 ID，首版指向 `mcp_tool.id`。
- `enabled`：绑定关系自身是否启用，首版管理端保存时默认启用。
- `sort`：展示和暴露顺序，首版按勾选顺序或工具原始顺序写入。

`provider_ref_id` 首版不加数据库外键到 `mcp_tool`。统一表后未来可能引用不同来源表，数据库层无法用单个外键表达多态引用。MCP 工具存在性和匹配关系由服务层校验。

## 后端接口

新增 Agent 工具绑定接口：

```text
GET /api/agents/{agentId}/tools
PUT /api/agents/{agentId}/tools
GET /api/agents/{agentId}/tools/options
```

建议权限：

```text
agent:tool:update
```

如果需要更细粒度，可以后续拆分：

```text
agent:tool:list
agent:tool:update
```

首版为了贴近现有 `agent:skill:update` 模式，可以使用单一 `agent:tool:update` 同时控制查询和保存。

绑定项返回：

```text
AgentToolBindingItem
  bindingId
  agentId
  toolName
  providerType
  providerRefId
  serverKey
  serverName
  toolDisplayName
  toolDescription
  serverEnabled
  toolEnabled
  enabled
  sort
```

可选项返回：

```text
AgentToolOptionItem
  toolName
  providerType
  providerRefId
  serverKey
  serverName
  remoteToolName
  exposedToolName
  displayName
  description
  serverEnabled
  toolEnabled
```

更新请求：

```json
{
  "tools": [
    {
      "toolName": "mcp.github.search_repositories",
      "providerType": "MCP",
      "providerRefId": 12,
      "sort": 1
    }
  ]
}
```

服务层校验：

- `agentId` 必须存在。
- `providerType` 首版只允许 `MCP`。
- `providerRefId` 必须对应存在的 `mcp_tool.id`。
- `toolName` 必须等于 `mcp.{serverKey}.{mcp_tool.toolName}`。
- 重复 `toolName` 自动去重，保留第一次。
- 已禁用的 MCP Server 或 MCP Tool 允许保存绑定，但运行时不会暴露。

允许保存禁用工具的原因：管理员可能临时全局停用某个 MCP 工具，Agent 的授权配置不应因此丢失。重新启用 Server 或 Tool 后，原绑定自动恢复生效。

## 运行时设计

`ToolExecutionContext` 增加 `agentId` 字段。`ChatService` 构建工具上下文时带上当前会话选择的 Agent ID。

`McpToolProvider.listTools(context)` 从全局可见改为 Agent 授权过滤：

```text
1. 如果 context.agentId 为空，不暴露 MCP 工具。
2. 查询 agent_tool_binding 中 agent_id = context.agentId、provider_type = MCP、enabled = true 的绑定。
3. 关联 mcp_tool 和 mcp_server。
4. 只返回 mcp_server.enabled = true 且 mcp_tool.enabled = true 的工具。
5. 工具名继续使用 mcp.{serverKey}.{remoteToolName}。
```

`McpToolProvider.execute(request, context)` 做二次校验：

```text
1. 解析 request.toolName 得到 serverKey 和 remoteToolName。
2. 如果 context.agentId 为空，返回失败结果。
3. 校验 Agent 是否绑定该 toolName。
4. 校验 MCP Server 是否启用。
5. 校验 MCP Tool 是否启用。
6. 通过后再调用 MCP Client。
```

未授权或禁用时返回工具失败结果，不中断聊天主流程：

```text
当前 Agent 未授权使用工具: mcp.github.delete_repo
MCP 工具未启用: mcp.github.delete_repo
MCP 服务未启用: github
```

这样即使模型或历史消息尝试调用未暴露工具，执行侧也不会绕过授权边界。

## 管理端设计

在 `admin-web/src/views/AgentsView.vue` 的操作列新增“绑定工具”，与“绑定 Skill”并列。

弹窗标题：

```text
绑定工具 - {Agent 名称}
```

弹窗内容：

```text
按 MCP 服务分组展示工具
每个工具显示：
  工具显示名
  暴露名称 mcp.{serverKey}.{toolName}
  描述
  全局状态：服务启用/停用，工具启用/停用
  勾选框：是否绑定到当前 Agent
```

交互规则：

- 打开弹窗时并行请求绑定列表和可选工具列表。
- 已绑定工具默认勾选。
- 禁用的 Server 或 Tool 显示状态标签，但绑定可以保留。
- 保存时提交当前勾选的 MCP 工具列表。
- 保存成功后关闭弹窗并显示中文成功提示。

首版不做复杂策略模板。工具数量较多时，可在弹窗内提供按服务名称、工具名称和暴露名称的本地过滤。

## 错误处理

管理接口使用统一 `ApiResponse` 和 `BusinessException`：

```text
Agent 不存在：NOT_FOUND，"Agent 不存在"
MCP 工具不存在：NOT_FOUND，"MCP 工具不存在"
toolName 与 providerRefId 不匹配：BAD_REQUEST，"工具标识与 MCP 工具不匹配"
providerType 非 MCP：BAD_REQUEST，"暂不支持该工具来源"
```

运行时授权失败使用 `ToolExecutionResult.failed`，内容为中文可读消息。运行时失败需要保留现有 MCP 调用日志行为：到达 MCP Client 前的授权失败不写 MCP 调用日志；已经进入 MCP 调用链路后按现有逻辑写调用日志。

## 验收标准

- 管理员可以给 Agent 精确绑定 MCP 工具。
- 未绑定 MCP 工具的 Agent 不会看到任何 MCP 工具。
- 已绑定但全局禁用的 MCP 工具不会暴露给 LLM。
- MCP 工具执行侧会二次校验 Agent 授权，不能绕过 `listTools`。
- MCP Server 全局启停、MCP Tool 全局启停和 Agent 绑定三层同时生效。
- 现有 Skill 绑定、MCP 服务管理、Sandbox 工具和聊天流程不受影响。
