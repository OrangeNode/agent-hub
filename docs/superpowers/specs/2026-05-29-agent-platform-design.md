# Agent 平台 RBAC 管理端对齐设计

## 目标

在当前单仓库项目基础上，完成一套可交付的 RBAC 管理闭环。交付结果包含：

- `admin-web`：前端页面、布局和交互体验对齐参考项目 `D:\project\agent-hub-v2-main`
- `backend`：使用现有 Java 多模块工程提供 RBAC 与动态菜单所需后端能力
- `docker/`：提供 PostgreSQL、Redis 等依赖服务部署目录，方便手动在服务器启动

本次设计强调“前端体验对齐”，不要求后端实现方式或工程结构对齐参考项目。

## 本次范围

本轮只覆盖管理端相关能力，聚焦以下内容：

- 登录认证
- 工作台基础壳子
- 用户管理
- 角色管理
- 菜单管理
- 动态菜单
- JWT 鉴权
- 统一响应与全局异常
- 依赖服务 Docker 化

明确不纳入本次范围的内容：

- `user-web` 页面改造
- AI 供应商、模型、MCP、Skill、Agent 管理页面对齐
- SSE 事件类型、事件协议和流内错误事件设计
- 后端实现方式对齐参考项目

## 总体策略

本次采用“前端体验对齐，后端能力托底”的策略。

`admin-web` 以参考项目的后台工作台风格为目标，尽量对齐页面结构、视觉密度、布局组织、菜单交互、标签页体验和 RBAC 页面模式。`backend` 保持现有 Spring Boot 多模块架构，只补足前端运行所需的 RBAC 与动态菜单接口，不追求与参考项目同名接口、同实现方式或同目录结构。`docker/` 目录单独提供依赖服务部署文件，不与应用运行脚本强耦合。

## 前端设计

### 参考对齐目标

`admin-web` 主要对齐以下体验：

- `AppLayout + Header + Sidebar + Tabs + Breadcrumb` 的后台主框架
- 浅色、克制、信息密度较高的企业后台样式
- 基于动态菜单的侧边栏渲染
- 基于当前路由的标签页管理
- 表格型 RBAC 管理页面
- 菜单树管理页面

本次对齐的是“页面形态、交互组织和使用方式”，不是简单替换颜色或局部组件。

### 页面与路由结构

`admin-web` 本轮路由收敛为：

- `/login`
- `/`
- `/dashboard`
- `/system/users`
- `/system/roles`
- `/system/menus`

其中：

- `/login` 为独立登录页
- `/` 为后台主框架入口，默认重定向到 `/dashboard`
- `/dashboard` 为工作台首页
- `/system/users` 为用户管理页
- `/system/roles` 为角色管理页
- `/system/menus` 为菜单管理页

### 布局与组件组织

`admin-web` 重构为以下核心界面结构：

- `AppLayout`：承载整体布局
- `Header`：顶部导航、面包屑、用户操作区
- `Sidebar`：动态菜单侧边栏
- `Tabs`：多标签页切换区
- `Breadcrumb`：当前路径展示

页面组织目标是直接进入可工作的后台界面，不做营销式首页，不堆装饰性卡片。

### 动态菜单机制

动态菜单按以下流程工作：

1. 用户登录成功
2. 前端保存 JWT
3. 前端请求当前用户信息
4. 前端请求当前用户菜单树
5. 菜单树转换为侧边栏菜单数据
6. 路由守卫根据登录状态与菜单状态决定跳转
7. 标签页根据访问路由自动维护

前端允许维护一份本地路由定义表，用于把后端菜单项映射到实际页面组件。这样既能保证页面结构稳定，也能兼容后端逐步演进。

### RBAC 页面设计

用户管理页采用“查询区 + 表格区 + 操作按钮 + 弹窗表单”的后台页面模式，支持：

- 用户列表查询
- 新增用户
- 编辑用户
- 删除用户
- 启停状态切换
- 绑定角色

角色管理页采用同样的管理模式，支持：

- 角色列表查询
- 新增角色
- 编辑角色
- 删除角色
- 状态切换
- 角色绑定菜单

菜单管理页采用树形管理模式，支持：

- 菜单树查询
- 新增同级或子级菜单
- 编辑菜单
- 删除菜单
- 调整显示顺序

本轮菜单管理页重点保证树形管理与基本编辑体验，不强求一次性覆盖所有增强交互。

## 后端设计

### 架构边界

后端继续使用现有多模块结构：

- `agent-hub-common`
- `agent-hub-security`
- `agent-hub-system`
- `agent-hub-ai`
- `agent-hub-agent`
- `agent-hub-chat`
- `agent-hub-server`

本轮真正需要补强的是 `system`、`security` 和 `server` 三个方向，让 `admin-web` 的 RBAC 与动态菜单真实可跑。

### 接口范围

后端提供以下接口能力：

- 认证
  - 登录
  - 获取当前登录用户信息
- 用户管理
  - 用户列表
  - 新增用户
  - 修改用户
  - 删除用户
  - 用户状态切换
  - 用户角色绑定
- 角色管理
  - 角色列表
  - 新增角色
  - 修改角色
  - 删除角色
  - 角色状态切换
  - 角色菜单绑定
- 菜单管理
  - 菜单树查询
  - 当前用户菜单树查询
  - 新增菜单
  - 修改菜单
  - 删除菜单
  - 菜单排序调整

本轮不要求后端 API 命名完全复刻参考项目，但会尽量保证前端调用简单清晰。

### 数据实现策略

后端采用“可运行优先、结构清晰优先”的实现策略：

- 服务层接口保持明确
- 控制器、服务、仓储边界保持清晰
- 当前可使用内存数据或轻量仓储实现跑通闭环
- 结构上为后续切换 PostgreSQL 持久化预留接口

这意味着本轮重点是把登录、RBAC、动态菜单和前端联调跑通，而不是一次性完成最终版数据库实现。

### 安全与统一规范

后端继续沿用现有统一规范：

- REST 接口统一使用 `ApiResponse`
- 错误码统一由 `ErrorCode` 定义
- 业务异常统一使用 `BusinessException`
- 全局异常由 `GlobalExceptionHandler` 处理
- JWT 登录认证和 Spring Security 权限控制继续统一管理

SSE 设计继续保持延期状态，本轮不扩展 SSE 事件协议。

## Docker 目录设计

项目根目录新增 `docker/`，至少包含：

- `docker-compose.yml`
- PostgreSQL 服务配置
- Redis 服务配置
- 中文部署说明

目标是让依赖服务部署独立于应用源码运行，你可以直接把该目录带到服务器，通过 Docker 手动启动数据库和缓存服务。

如有必要，可增加环境变量样例文件，但不要求在本轮引入复杂编排。

## 数据流

### 登录与初始化

1. 用户在 `admin-web` 登录
2. 后端校验用户名和密码并返回 JWT
3. 前端保存令牌
4. 前端请求当前用户信息
5. 前端请求当前用户菜单树
6. 前端渲染后台主框架与动态菜单

### RBAC 管理

1. 用户进入用户、角色或菜单页面
2. 前端调用对应管理接口
3. 后端返回统一响应结构
4. 前端根据结果刷新表格、树和表单状态

### 动态菜单生效

1. 后端根据当前用户角色计算可见菜单
2. 前端根据菜单树构建侧边栏
3. 用户角色或菜单关系调整后，重新加载菜单即可体现权限变化

## 错误处理

普通 REST 接口继续使用统一响应结构：

```json
{
  "code": 0,
  "message": "ok",
  "data": {}
}
```

后端负责统一处理：

- 参数校验错误
- 认证失败
- 授权失败
- 业务异常
- 未知异常

前端 Axios 拦截器负责：

- 统一错误提示
- 登录失效后的状态清理
- 自动跳转回登录页

SSE 相关事件格式不纳入本轮统一设计。
